Cipher's landing page needed four feature cards — each with an animated visual that explains a core workflow at a glance. No static screenshots. No Lottie files. Real, interactive React animations that respond to the page's theme and design tokens.

I built all four in a single session using Gemini's Canvas mode. Here's how that worked, what surprised me, and how I made the output production-ready.

## What I mean by "vibe animating"

Vibe coding gets talked about a lot in the context of shipping features fast. Vibe _animating_ is a more specific version of that: using AI to rapidly explore motion ideas, iterate on timing and choreography, and land on something that feels right — without writing every keyframe by hand.

The process is more like directing than programming. You describe what the animation should communicate, show the AI what you have so far, and steer it toward something that matches the visual language of your project.

Gemini Canvas was especially good for this because it renders the output live as you iterate. You see the animation running, say "make the transition snappier" or "stagger the dots instead of fading them all at once," and the canvas updates in place. That feedback loop is what makes it feel like animating rather than coding.

## Making AI-generated animations work with a real token codebase

The hardest part wasn't generating the animations. It was integrating them into a codebase where colors, spacing, and typography are all driven by CSS custom properties that change based on theme and user personalization.

Gemini Canvas gives you working React code, but it tends to hardcode colors as hex values and sizes as pixel literals. That's fine for a prototype, but it breaks the moment someone switches to dark mode or changes their brand color.

The fix was a shared `useTokenColors` hook that resolves CSS custom properties to computed values at runtime. Every animation reads its colors from the design token system instead of hardcoded values:

```tsx
const colors = useTokenColors({
  primary: "var(--primary)",
  border: "var(--border)",
  muted: "var(--muted)",
  card: "var(--card)",
});
```

This means all four animations automatically adapt when the theme changes — same animation logic, different palette. That's the kind of thing AI won't do on its own, but it's trivial to add once you have the pattern.

The other shared piece is a `useVisible` hook that pauses animations when they scroll out of view. Without it, you'd have four complex animations running simultaneously whether anyone can see them or not.

## What worked well about the Gemini Canvas workflow

**Speed of exploration.** I could try three different choreography ideas for the same concept in the time it would normally take to implement one. Most of the value came from seeing bad ideas fail fast.

**Consistent visual language.** By feeding Gemini the output of the first animation as context for the second, the four cards ended up with a shared visual language — similar line weights, similar timing curves, similar use of color — without me having to manually enforce a style guide.

**Live preview.** Canvas mode renders the animation as you iterate. This is fundamentally different from generating code and then switching to a browser to see it. The feedback loop is tight enough that you can steer the animation's feel, not just its logic.

## What I had to fix manually

**Token integration.** Every hardcoded color had to be replaced with `useTokenColors`. This was mechanical but important.

**Performance.** The initial output used `requestAnimationFrame` loops and inline style recalculations that caused unnecessary re-renders. Switching to Motion (Framer Motion) for the animation runtime and `useVisible` for pause/resume made them production-ready.

**Sizing.** Canvas doesn't know about your layout constraints. Each animation needed to be refactored to fill its `aspect-video` container responsively rather than using fixed dimensions.

## The takeaway

AI-assisted animation isn't about removing the craft. It's about compressing the exploration phase. The iteration from "here's what I want this to communicate" to "here's a working animation that does it" went from days to hours.

But the integration work — making it theme-aware, performant, and responsive — is still manual. That's where the design engineering judgment lives, and it's the part that makes the difference between a demo and a product.
